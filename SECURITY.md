# Security Policy

## Supported Versions

Only the latest release branch of Armaxcoin receives active security patches.

| Version | Supported          | Status |
| ------- | ------------------ | ------ |
| 1.0.x   | :white_check_mark: | Active Public Testnet |
| < 1.0.0 | :x:                | Deprecated / Pre-Release |

---

## Reporting Security Vulnerabilities

We take the security of the Armaxcoin network and its users seriously. If you discover a security vulnerability or consensus flaw (including integer overflows, reentrancy, consensus splits, transaction malleability, or remote code execution), please report it responsibly.

### Responsible Disclosure Process

1. **Do NOT open a public GitHub issue** for undisclosed security vulnerabilities.
2. Please submit your vulnerability report directly via **GitHub Private Vulnerability Reporting** on the repository:
   - Navigate to the repository's `Security` tab -> `Advisories` -> click `Report a vulnerability`.
3. Please include detailed technical information in your report:
   - Vulnerability category and potential impact.
   - Detailed step-by-step replication instructions or a Proof of Concept (PoC).
   - Any suggested remediations or mitigations.

### Response Timeline

- **Initial Acknowledgment:** Within 48 hours of receipt.
- **Triage & Assessment:** Within 5 business days.
- **Patch Development & Advisory:** Coordinated release with reasonable embargo period until node operators update.

## Threat Model & Security Boundaries

### 1. RPC & Local Service Interface
- By default, the Armaxcoin RPC daemon (`armcoind`) binds strictly to loopback interface `127.0.0.1:19332` on mainnet (`127.0.0.1:19333` on testnet).
- All upcoming auxiliary local services (API Explorer `19340`, Web Explorer `19341` (Planned / Removed), Wallet API `19342`, Metrics `19343`) are also designed and specified to bind strictly to `127.0.0.1` loopback by default.
- Mutating endpoints (`/mine`, `/block/submit`, `/peers`) require valid authentication or local non-CORS context.
- If exposed to external networks via `-rpcbind 0.0.0.0`, administrators MUST configure strong HTTP Basic Auth credentials and a TLS certificate/key (`ARMX_RPC_TLS_CERT`, `ARMX_RPC_TLS_KEY`). The daemon rejects a public RPC bind without both controls.

### 2. P2P Transport Layer
- Armaxcoin P2P transport operates on port `19334` (mainnet) and `19335` (testnet) with TLS 1.3 and TOFU pinning enabled by default. Plaintext fallback is a legacy-testnet-only opt-out and must never be enabled for a value-bearing network.
- **Strict TLS (`require_tls: true`):** Forbids unencrypted TCP fallback on all connections and is enabled by default.
- **TOFU Pinning (`p2p_tofu: true`):** Is enabled by default and pins the remote certificate public-key fingerprint after a successful first contact. Any mismatch or persistence failure terminates the connection before application payload transmission. The first contact still needs an out-of-band trusted seed fingerprint to resist an active first-contact MITM.
- **Identity handling:** A missing P2P identity is generated once. An existing identity that is unreadable, empty, or invalid fails closed and must be restored explicitly; it is never silently replaced.

### 3. Keystore Security
- Private keys generated by `armwallet` or desktop GUI are derived from a 24-word BIP-39 mnemonic (HKDF-SHA256 into a 32-byte seed) and stored in encrypted keystore files using Argon2id key derivation and authenticated encryption (AES-256-GCM / XChaCha20-Poly1305) with restricted permissions (`0600`).
- Private keys are NEVER transmitted to the RPC daemon node. All transaction signing occurs strictly client-side.
- Users are solely responsible for securing their 24-word recovery mnemonic and preventing physical/malware access to keystore files.

### 4. Consensus & Cryptographic Status
- Armaxcoin Layer-1 consensus implements the NIST FIPS 204 ML-DSA-65 digital signature algorithm for all user transactions; the implementation has not been independently audited or validated (no CMVP validation).
- PoW SHA-256 mining remains bounded by ~128 bits of post-quantum security against Grover's algorithm.
- Advanced experimental extensions such as Hash Time-Locked Contracts (`HTLC`) remain in forward-compatible library status.
- **Audit Status:** The core implementation and PQC consensus code have not yet been evaluated by an external third-party cryptographic security audit.

### 5. Known Limitations & Threat Model Disclosures
- **P2P Transport Security:** Traffic is encrypted with TLS 1.3 using a persistent, self-signed ECDSA P-256 node identity stored in `p2ptls.pem`. TOFU pins the remote certificate public-key fingerprint after first contact; identity is not verified through a PKI/CA, so the initial contact remains vulnerable to an active man-in-the-middle unless fingerprints are distributed out-of-band.
- **Code Audit Status:** The cryptographic implementations and consensus engine are in active testnet development and have not yet undergone a formal external security audit.
- **PoW Algorithm Evolution:** Historical blocks 0..519 were mined using double-SHA256 (SHA-256d), and blocks 520..2499 used ArmaxHash v1 (Argon2id 2048 KiB, $t=2, p=1$; see `docs/CONSENSUS_AND_NETWORK.md`). Active mining from block #2500 onwards enforces **ArmaxHash v2 Stream-Fast** (chained BLAKE2b), engineered to eliminate DRAM memory churn and facilitate high-throughput CPU mining across commodity hardware and mobile/ARM devices without claiming permanent ASIC immunity.
- **Early 51% Hashrate Vulnerability:** Low initial network hashrate during early testnet and launch phases leaves the blockchain vulnerable to 51% deep reorganization attacks. Reorganizations are strictly bounded by `MaxReorganizationDepth = 720` blocks.
- **ARM Verification Performance:** ML-DSA-65 verification involves matrix-vector polynomial multiplication that imposes measurable CPU latency on constrained ARM single-board computers (Raspberry Pi / Orange Pi).
- **Minimum Go Version:** Building from source strictly requires Go 1.27 or higher due to the standard library `crypto/mldsa` implementation and toolchain alignment (`go.mod`).
