## 1. Overview & Purpose

Armaxcoin v1.0.7 addresses six core functional and security objectives for operators on the public Testnet:

1. **Tightens the future-timestamp rule** (proposal C6) with a single hard fork at block 20,000, and adds miner-side protection so a fast local clock no longer wastes a block.
2. **Reduces sync and storage cost**: incremental persistence during sync, optional BoltDB record compression, and per-request compressed block ranges.
3. **Hardens the P2P layer**: inbound handshake timeout, persistent ban store, optional pinned seed fingerprints, and `PUSH_BLOCKS` so a node behind NAT can deliver blocks to a public peer that cannot dial back.
4. **Hardens operational security and subsystem stability (Group A Security Fixes)**: closes critical CSRF/Host-header vulnerabilities in the Web GUI, synchronizes P2P certificate fingerprints with SPKI pinning, bounds in-memory address translation caches, guards miner difficulty adjustments against Inf/NaN arithmetic faults, eliminates mnemonic leakage via CLI arguments, enables DEFLATE decompression on `PUSH_BLOCKS`, prioritizes `X-Mine-Key` authentication without triggering IP lockouts, separates cross-chain validator multisig key custody, and repairs local bridge deployment contracts.
5. **Hardens consensus parameter security and supply accounting (Group B Consensus Fixes)**: permanently locks PoW activation heights against environment variable manipulation on public networks (`HIGH-02`), and fixes circulating supply calculations across storage replays, live block validations, and reorgs to account for actual minted coinbase subsidies (`HIGH-04`).
6. **Hardens P2P and chain state concurrency & sync reliability (Group C Reliability Fixes)**: eliminates map data races on in-memory undo records during reorganizations via a dedicated RWMutex (`HIGH-01`), stages multi-chunk pushed blocks in peer sessions to prevent reorg dropouts (`HIGH-07`), and enforces cryptographic hash continuity with automatic ban penalties during IBD chunk synchronization (`HIGH-09`).

### Network & Consensus Invariance

- **Changed (consensus):** the future-timestamp limit only. Below block 20,000 the 2-hour limit still applies, so every existing block stays valid. The rule only **narrows** the set of accepted blocks.
- **Unchanged:** genesis, NetworkID, Proof of Work timeline (Double-SHA256 for $H < 520$, ArmaxHash v1 for $520 \le H < 2500$, ArmaxHash v2 Stream-Fast for $H \ge 2500$), 120-second target block time, LWMA-1 difficulty ($N=60$), MTP-11/MTP-55 timestamp rules (C1/C2), block reward (60 tARMX), halving interval (1,050,000 blocks), supply cap (126,000,000 ARMX), Merkle calculation, and ML-DSA-65 signatures. Group B preserves all consensus invariants: PoW algorithms, halving boundaries, block subsidy schedules, and the 126,000,000 ARMX cap remain strictly identical.
- **Not part of this fork:** C3 (audit only), C4 (TTL), C5 (reorg policy), and any LWMA change. They have no approved specification and are excluded so the effect of the timestamp rule stays attributable. The earlier plan to fork at block 15,000 was dropped in favour of this single fork.
- **Wall-clock caveat:** the future-timestamp check uses the validator's local clock, so it is not a pure function of chain data. Historical replay (`isHistorical`) skips it, so stored blocks never become invalid after a restart.
- **Storage Compatibility:** default storage is unchanged (plain JSON records). Optional compression writes a new record form that v1.0.6 cannot read (Section 3).
- **Wire Compatibility:** P2P framing and the handshake are unchanged. The new fields (`accept`, `enc`, `z`) and message (`PUSH_BLOCKS`) are ignored by v1.0.6 nodes.

### Group A: Security & Operational Fixes

In addition to the C6 timestamp consensus fork and storage efficiency features, v1.0.7 addresses critical security and operational findings without changing block consensus or network ledger rules:

1. **CRIT-01 (Web GUI Authentication & Host Validation):**
   - Target: `gui/main_unix.go`
   - Added `initSessionToken()` generating a random 32-byte hex token (`X-Armx-GUI-Token`) saved to a local `.session` file (mode 0600).
   - Wrapped all API handlers with `secureGUIHandler()` which verifies the `Host` header against loopback addresses (`127.0.0.1`, `localhost`, `::1`) and validates the session token.
   - Mandated wallet passphrase verification on `/api/send` before signing transactions.

2. **CRIT-02 (P2P Identity SPKI Fingerprint):**
   - Target: `node/p2p_crypto.go`, `node/node_identity_spki_test.go`
   - Changed `InitNodeIdentity()` to compute SHA-256 over `RawSubjectPublicKeyInfo` instead of the raw ASN.1 certificate.
   - Ensures identity fingerprints strictly match the pinning format used by `seed_pins.go` and `extractCertPubkeyFingerprint`.

3. **CRIT-04 (Local Bridge Deployment Scripts):**
   - Target: `contracts/scripts/deploy-local.cjs`
   - Updated constructor invocation for `WrappedArmaxcoin.sol` from 4 arguments to 6 arguments (`admin, sourceNetworkHash, genesisHash, bridgeId, validators, admin`), restoring clean deployment on local EVM.

4. **HIGH-03 (Bounded Address Cache Memory Cap):**
   - Target: `core/address.go`, `core/address_cache_test.go`
   - Replaced unbounded `sync.Map` `addrHexCache` with a bounded cache structure protected by `sync.RWMutex`.
   - Capped capacity at 10,000 entries with automatic 20% eviction when full, mitigating memory exhaustion under transaction floods.

5. **HIGH-05 (Mining RPC Difficulty Arithmetic Guard):**
   - Target: `miner/miner.go`
   - Added `!math.IsInf(newDiff, 0) && !math.IsNaN(newDiff)` checks to Stratum `set_difficulty` processing, preventing silent thread panics or corruption.

6. **HIGH-06 (Interactive Masked Recovery Mnemonic Entry):**
   - Target: `cli/armwallet/main.go`, `cli/armwallet/main_test.go`
   - Added `-restore-interactive` flag using `golang.org/x/term` masked password input (with standard input fallback for scripts).
   - Added an explicit security warning when mnemonics are passed via command-line arguments to discourage process table exposure.

7. **HIGH-08 (`PUSH_BLOCKS` DEFLATE Payload Decompression):**
   - Target: `node/p2p.go`, `node/p2p_compress_test.go`
   - Added `pr.expandBlocks()` call inside `PUSH_BLOCKS` message handling.
   - Enables compressed block ranges to be properly unpacked and propagated across NAT connections instead of being silently dropped.

8. **HIGH-10 (`X-Mine-Key` Priority Verification & IP Lockout Prevention):**
   - Target: `node/server.go`, `node/v106_maintenance_test.go`
   - Prioritized `X-Mine-Key` header matching before falling back to HTTP Basic Auth.
   - Clears transient failure records via `globalAuthLockout.recordSuccess(clientIP)`, preventing CPU/remote miners from being locked out due to missing Basic Auth headers.

9. **HIGH-11 (Cross-Chain Multisig Custody Separation):**
   - Target: `bridge/evm_multisig_writer.go`, `bridge/local_evm_writer.go`, `bridge/multisig_aggregator_test.go`
   - Added `RemoteValidatorClient` interface and `MultisigAggregator` type to orchestrate attestation signing across independent validator instances.
   - Added operational warnings clarifying that `LocalEVMWriter` is exclusively for local test fixtures and must not be used in production environments.

### Group B: Consensus-Sensitive Fixes

Group B targets consensus parameter hardening and storage replay supply accuracy while strictly preserving all existing consensus rules (PoW algorithms, halving schedule, block subsidy arithmetic, and the 126,000,000 ARMX total cap):

1. **HIGH-02 (Lock Consensus Fork Activation Heights on Production Networks):**
   - Target: `core/network.go`, `core/network_override_test.go`
   - Guarded `GetArmaxHashActivationHeight` and `GetArmaxHashV2ActivationHeight` environment variable checks with `if ActiveNetwork.Name == "regtest"`.
   - On `mainnet` and `testnet`, `ARMX_ARMAXHASH_HEIGHT` and `ARMX_ARMAXHASH_V2_HEIGHT` are strictly ignored, ensuring fixed constants (e.g. Testnet ArmaxHash at 520, ArmaxHash v2 at 2500) cannot be altered on live nodes.
   - Preserves environment overrides exclusively on `regtest` for developer testing and regression rehearsals.

2. **HIGH-04 (Circulating Supply Calculation Parity on Disk Replay and Reorgs):**
   - Target: `core/blockchain.go`, `core/storage.go`, `core/consensus.go`, `core/supply_underclaim_test.go`
   - Added `BlockMintedSubsidy(b *Block, maxAllowedReward int64) int64` which computes net minted coinbase subsidy (`coinbaseAmount - totalFees`, floored at 0 and capped at max allowed reward), preventing recycled transaction fees from being erroneously counted as newly minted coins.
   - Updated disk replay loops in `core/storage.go` (`loadBlockchainFromPath`), full revalidation in `RebuildState()`, live block addition in `ValidateAndAddBlock()`, and chain reorganization in `ResolveFork()` to accumulate `BlockMintedSubsidy`.
   - Guarantees 100% mathematical supply parity across live nodes, restarted nodes, and reorganized branches even when miners intentionally underclaim block subsidies.

### Group C: P2P & Chain State Reliability

Group C addresses concurrency safety and synchronization robustness while strictly preserving the heaviest cumulative chainwork selection rules:

1. **HIGH-01 (Data Race on `undoHistory` Map Protection):**
   - Target: `core/blockchain.go`, `core/store.go`, `core/consensus.go`, `core/storage.go`, `core/undo_race_test.go`
   - Added a dedicated `undoLock sync.RWMutex` to `core.Blockchain` and implemented `cloneBlockUndoRecord()` to return isolated copies of undo records.
   - Synchronized all reads and writes across `GetBlockUndoRecord()`, `SaveBlockToStore()`, `ValidateAndAddBlock()`, and `ResolveFork()`, eliminating fatal `concurrent map read and map write` crashes under concurrent validation and reorgs.

2. **HIGH-07 (Multi-Chunk `PUSH_BLOCKS` Staging Reorg Buffer):**
   - Target: `node/fork_push.go`, `node/p2p_push_chunk_test.go`
   - Added `pushBufferSession` per peer in `handlePushedBlocks()` with a 30-second TTL to stage sequential partial chunks of a competitor branch.
   - When intermediate chunks alone have lower chainwork than the local tip, they are staged in memory; once remaining chunks arrive and cumulative chainwork exceeds the local tip, `ResolveFork()` executes cleanly on the complete candidate branch.
   - Removed artificial `SyncChunkSize` push abortion in `pushChainToPeer()`, allowing multi-chunk pushes up to `MaxPushBlocks` (1,000 blocks).

3. **HIGH-09 (IBD Sync Cryptographic Linkage Verification & Ban Scoring):**
   - Target: `node/p2p.go`, `node/ibd_verification_test.go`
   - Added `br.Blocks[i].PrevHash != br.Blocks[i-1].Hash` checks during initial block download chunk accumulation to reject corrupted or spoofed block ranges early.
   - Enforced immediate misbehavior penalty (`p.AddBanScore(peerIP, 50)`) and recorded peer failure (`p.RecordPeerFailure(syncPeer)`) when a peer delivers broken or non-contiguous segments.
   - Added peer failure tracking and ban scoring on invalid `ResolveFork()` failures to prevent nodes from repeatedly querying malfunctioning or malicious sync peers.

### Deliberately Not Implemented

- **INV_TX / GET_TX transaction announcement and compact blocks:** measured data showed only 191 transfers in 9,273 blocks, and INV needs per-peer capability state. Not worth the complexity now.
- **State root accumulator:** Deferred to subsequent major milestone (v1.1.0) pending Merkle-tree state benchmarking.
- **Falcon signatures:** Excluded from the cryptographic roadmap in favor of standardizing NIST FIPS 204 (ML-DSA-65) exclusively.
- **5-minute future limit:** may be considered later, only after miner clocks are corrected.

## 3. Upgrade & Rollback Instructions

### For Node Operators (`armcoind`):
1. **Upgrade before block 20,000.** Stop the node, replace the binary, start it:
   ```bash
   kill -SIGINT <armcoind-pid>
   ./armcoind -network testnet
   ```
2. Verify the version:
   ```bash
   curl -s -u <user>:<pass> http://127.0.0.1:19333/status | jq .version
   # Expected output: "1.0.7"
   ```
3. Ensure time synchronization (`timedatectl set-ntp true` on Linux, `w32tm /resync` on Windows).
4. Do **not** enable `store_compression` on a node you may need to roll back.

### For Miners (`armminer`):
- Upgrade the miner and the node it talks to. Pool or stratum operators must fix the clock on the host that builds block headers.

### Rollback Path:
- **Without compression enabled:** replace the binary with v1.0.6. No database change is required. Note that a v1.0.6 node will follow blocks that v1.0.7 rejects after block 20,000 (Section 7).
- **With compression enabled:** stop the node first, then convert, then start v1.0.6:
  ```bash
  ./armcoind -network testnet -datadir <dir> -store-rewrite plain
  ```
  Back up the database before converting.

## 5. Miner Compatibility

- `armminer` still reaches the node through HTTP RPC (`GET /getmininginfo`, `GET /getblocktemplate`, `POST /block/submit`) or an external Stratum v1 pool; the RPC schema is unchanged.
- The new clock correction runs only in the local RPC mining path. Stratum and remote miners keep stamping with their own clock, so they must be NTP-synchronized.
- In the last 1,000 blocks of the explorer backup, six addresses mined (two of them about 38 % each), so a small number of operators determine consensus adoption at block 20,000. Operators cannot be identified from chain data alone; coordinated upgrade advisories must be broadcast across community mining pools and public node channels prior to activation height.

## 7. Known Limitations & Verification Status

- **[KNOWN LIMITATION] Chain-split risk:** After block 20,000, an un-upgraded miner whose clock is more than 10 minutes fast can build blocks that v1.0.6 nodes accept and v1.0.7 nodes reject. The only mitigation is upgrading all miners and validators before the fork height.
- **[KNOWN LIMITATION] Non-deterministic rule:** A validator with a slow clock may reject a block that others accept; the clock-aware miner and NTP reduce but do not remove this.
- **[KNOWN LIMITATION] Noisy retries:** A v1.0.7 node that rejects a peer's forward-stamped candidate chain retries the same peer repeatedly. This is harmless but fills the log.
- **[KNOWN LIMITATION] `-noseeds` and `-peers`:** `-noseeds` also disables `-peers` (pre-existing behaviour). Isolated tests that need explicit peers must not pass `-noseeds`.
- **[VERIFIED] `PUSH_BLOCKS` scope & multi-chunk staging (`HIGH-07`):** Competitor branches that replace blocks on the peer are staged across sequential chunks in `pushBufferSession` (30s TTL) up to `MaxPushBlocks = 1000` blocks and a 30s per-peer cooldown, executing reorganization cleanly when cumulative chainwork exceeds the local tip.
- **[KNOWN LIMITATION] Storage compression downgrade:** Compression is not readable by v1.0.6 and is off by default. Downgrading requires running `-store-rewrite plain` prior to switching to v1.0.6. Coinbase-only blocks are too small to benefit.
- **[VERIFIED] Test harness & regression pass:** Full unit test suite (`go test -tags testhooks ./...`) passes 100% across all 15 packages in the repository. Bridge test fixtures (`sim01_deposit_test.go` and Ganache validator attestation) pass cleanly in local testing.
- **[NOT VERIFIED] Real WAN/NAT deployment:** While verified under local loopback multi-process simulation, real WAN/NAT deployment and live multi-VPS rehearsal have not yet been performed.
- The cross-chain bridge is a separate workstream and is not part of this core release.
