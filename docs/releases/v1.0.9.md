## 1. Executive Summary & Purpose

Armaxcoin v1.0.9 is a critical consensus recovery, miner performance, and desktop GUI stability release designed to immediately unstick the public testnet from **Block `#13,292`** during a sudden hashrate drop, multiply standalone CPU miner (`armminer`) throughput by up to **5.45x**, and complete seamless single-binary desktop GUI startup for Unix and Linux environments.

The release delivers three major improvements:

1. **Testnet Anti-Stall Emergency Difficulty Adjustment (TEDR - Model 3 at Block `#13,293`):** Introduces a forward-only, non-invasive consensus recovery mechanism activating at **Block `#13,293` on Testnet** (immediately after the stalled tip `#13,292`). When high-throughput compute leaves the network and leaves difficulty elevated at Difficulty 10, any block interval exceeding **1,200 seconds (20 minutes)** qualifies for an emergency stall-breaker target (`ArmaxHashPowLimit`, Difficulty 3). Under Model 3 Synthetic Normalization, the chain unsticks immediately and recovers smoothly to normal 120-second CPU mining without risk of permanent lock or moving-average contamination.
2. **Zero-Allocation CPU Miner (`armminer`) Hot-Path Optimization & Canonical Benchmark Fix:** Eliminates per-nonce `fmt.Sprintf`, `hex.DecodeString`, `big.Int.SetString`, and mutex contention in `armminer`'s HTTP (`getblocktemplate`) and Stratum v1 mining loops. Achieves **`0 B/op` and `0 allocs/op`** in the inner nonce loop, increasing 8-thread CPU hashing throughput from **`1.13 MH/s` to `6.16 MH/s` (`5.45x` speedup / `+444.5%`)** while preserving 100% bit-for-bit hash equivalence. Also updates `armminer -benchmark` and `armaxhash` benchmarks to measure realistic 284-byte canonical `ArmaxHash v2` block headers (`Index = 13052`) rather than synthetic 80-byte or Genesis `SHA-256d` (`Index = 0`) workloads.
3. **Linux/Unix Desktop GUI Daemon Auto-Start (`gui/main_unix.go`):** Resolves the requirement on Linux and macOS where users had to manually run `armcoind` in a separate terminal before launching `armgui`. `./armgui` now automatically launches an embedded background node when targeting loopback RPC, identical to the Windows desktop experience.

## 2. Problem Statement & Root Cause Analysis

### A. Hashrate Shock & Testnet Stall at Block `#13,292`
* **Symptoms:** Active testnet miners pushed network hashrate to **~2.37 GH/s**, raising difficulty to **Difficulty 10** ($1.1 \times 10^{12}$ hashes per block). When the high-throughput miner disconnected after Block `#13,292`, the testnet stalled for over 13 hours because standard CPU miners require **~20+ hours** per block at Difficulty 10.
* **Root Cause:** The LWMA-1 algorithm evaluates a 60-block sliding window and clamps solve times to $6 \times T = 720\text{s}$. If hashrate drops by $99\%$, clearing 60 blocks of Difficulty 10 at ~20 hours per block would require **over 50 days of continuous mining**, during which the testnet remains frozen. Setting `AntiStallActivationHeight = 13293` allows the very next block (`#13,293`) to immediately trigger emergency recovery once nodes upgrade to v1.0.9.

### B. CPU Miner (`armminer`) Per-Nonce Allocation Overhead & Benchmark Misrepresentation
* **Symptoms:** `armminer` achieved only `~1.13 MH/s` across 8 threads on an Intel Core i5-8365U CPU, despite the underlying `armaxhash.HashV2` kernel supporting much higher throughput. Furthermore, `armminer -benchmark` constructed a synthetic block with `Index: 0`, inadvertently benchmarking legacy Genesis `SHA-256d` instead of `ArmaxHash v2`.
* **Root Cause:**
  1. On every nonce iteration, `armminer` called `b.HeaderBytes()` (`fmt.Sprintf("%d:%d:%s:%s:%d:%s", ...)`), `armaxhash.HashV2(b.HeaderBytes(), ...)` (allocating a new 312-byte buffer per call), `fmt.Sprintf("%x", sum)` (hex-encoding the 32-byte digest), and `core.HashMeetsTarget` (`hex.DecodeString` + `new(big.Int).SetString`), causing **13 heap allocations (`888 B/op`) per nonce** and severe Go garbage-collector pressure across worker goroutines.
  2. In Stratum v1 mode (`runStratumMiningSession`), every worker locked and unlocked `c.stateMu.RLock()` on **every single nonce**, causing cache-line bouncing across CPU cores.

### C. Linux GUI Requiring Manual Daemon Startup
* **Symptoms:** In v1.0.8 on Linux/macOS, executing `./armgui` resulted in connection errors and `502 Bad Gateway` unless `armcoind` was launched first in another terminal session.
* **Root Cause:** In `gui/main.go` (Windows), `verifyNodeNetwork` checks the local node and, if offline, automatically spawns an embedded daemon via `core.OpenBlockchain` and `node.StartServerWithConfig`. In `gui/main_unix.go`, this embedded node auto-launcher was missing, expecting an external daemon to already be running.

## 3. Technical Solutions & Implementation

### A. Testnet Anti-Stall Consensus Rules (`core/network.go`, `core/target.go`, `core/consensus.go`, `node/p2p.go`, `node/server.go`)
1. **Activation Height:** Activated deterministically at **Block `#13,293`** on Testnet (`TestnetProfile.AntiStallActivationHeight = 13293`). Mainnet is permanently excluded (`MainnetLaunched = false`, `AntiStallActivationHeight = -1`).
2. **Emergency Eligibility ($\Delta t > 1,200\text{s}$):**
   A candidate block $B_i$ qualifies for the emergency target if and only if:
   $$B_i.\text{Index} \ge 13{,}293 \quad \land \quad (B_i.\text{Timestamp} - B_{i-1}.\text{Timestamp}) > 1{,}200\text{s} \quad \land \quad \neg \text{IsMainnet}$$
3. **Emergency PoW Target:** Validated against `ArmaxHashPowLimitHex` (`000fffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff`, Difficulty 3 / 4,096 expected hashes), allowing commodity CPUs to solve the stall-breaker block in milliseconds.
4. **Model 3 Synthetic Target Normalization:**
   When emergency blocks are processed inside the 60-block LWMA window:
   - Solve time is normalized to `maxSolveTime = 720 seconds`.
   - Target is normalized to the last legitimate non-emergency target (`lastNormalTarget`).
   - The low emergency target is never leaked into `sumTargets`, preventing moving-average collapse.
5. **P2P Relay Filter Protection:** Updated `node/p2p.go:1591` so nodes do not penalize peers broadcasting valid emergency blocks.
6. **Pool & RPC Template Support:** Updated `node/server.go:/getblocktemplate` to automatically serve the emergency target when local time exceeds 20 minutes from the last block.

### B. Zero-Allocation CPU Miner Hot-Path & Benchmark Fixes (`miner/miner.go`, `miner/miner_test.go`, `armaxhash/armaxhash_test.go`)
1. **Pre-Built Header Prefix/Suffix (`buildHeaderPrefixBytes`, `buildHeaderSuffixBytes`):** Constructs `<Index>:<Timestamp>:<PrevHash>:<MerkleRoot>:` and `:<Miner>` once per job/timestamp update. Per-nonce header assembly uses `strconv.AppendInt(headerBuf[:prefixLen], nonce, 10)` into a stack-allocated `[384]byte` buffer.
2. **In-Place `ArmaxHash v2` Digest Computation (`computeHeaderDigestBytes`):** Writes the 28-byte domain prefix (`"ARMAXHASH-V1\x00\x02\x0e\x00ARMX-TESTNET-1"`) once into a worker-local `[512]byte` buffer and streams Stage-1 and Stage-2 BLAKE2b directly without heap allocations.
3. **Zero-Allocation 32-Byte Target Comparison (`bigIntToTargetBytes32`, `hashBytesMeetTarget32`):** Replaces per-nonce hex encoding/decoding and `big.Int` allocation with a direct 32-byte big-endian comparison (`bytes.Compare(hash[:], targetBytes[:]) <= 0`), only formatting `b.Hash` when a winning block or share is actually found.
4. **Batched Stratum Mutex Reads:** Checks `c.stateMu.RLock()` for job changes once every **256 hashes** (`nonceCount & 0xFF == 0`) instead of on every nonce, eliminating multi-core RWMutex contention.
5. **Measured Performance Gains (`Intel Core i5-8365U @ 1.60GHz`, `go test -bench=BenchmarkMinerHotLoop -benchmem -cpu="1,4,8" ./miner`):**
   - **1 Thread:** `2,710 ns/op` (`0.37 MH/s`, `888 B/op`, `13 allocs/op`) $\to$ **`806.7 ns/op` (`1.24 MH/s`, `0 B/op`, `0 allocs/op`) — `3.36x` speedup**
   - **4 Threads:** `1,125 ns/op` (`0.89 MH/s`, `888 B/op`, `13 allocs/op`) $\to$ **`285.0 ns/op` (`3.51 MH/s`, `0 B/op`, `0 allocs/op`) — `3.95x` speedup**
   - **8 Threads:** `884.3 ns/op` (`1.13 MH/s`, `888 B/op`, `13 allocs/op`) $\to$ **`162.4 ns/op` (`6.16 MH/s`, `0 B/op`, `0 allocs/op`) — `5.45x` speedup (`+444.5%`)**

### C. Linux Embedded Node Auto-Launcher (`gui/main_unix.go`)
1. **Loopback Detection (`isLoopbackRPC`):** Automatically detects if `rpcURL` targets loopback addresses (`127.0.0.1`, `localhost`, `::1`).
2. **Embedded Server Startup:** If loopback RPC is offline, opens database handle (`core.OpenBlockchain(3)`) and starts the embedded daemon goroutine (`go node.StartServerWithConfig(bc, cfg)`).
3. **Ready-State Polling Loop:** Polls `/api/stats` every 100ms for up to 5 seconds until the embedded daemon reports ready before launching the browser UI.
