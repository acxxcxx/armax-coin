# Armaxcoin v1.0.11 — Release Documentation

**Target Release:** Armaxcoin v1.0.11 — Backward-Compatible Consensus Transition, Unified Block `#20,000` Activation (`C6` + `TxBinaryV1`), Adaptive C2/C6 Miner Margin, and Bounded ASERT Cache  
**Network Compatibility:** Full rolling backward compatibility with `v1.0.10` on `ARMX-TESTNET-1` (`#15,967`–`#19,999`)  
**Software Version Identifier:** `core.Version = "1.0.11"`  
**Mainnet Launch Lock:** `core.MainnetLaunched = false` (Mainnet launch remains locked; `ARMX-MAINNET-1` profile pre-configured for future launch)  
**Target Activation Milestones (`ARMX-TESTNET-1`):**
- **Block `#13,335` (Active):** Armax-ASERT-AW Difficulty Adjustment (`MaxASERTBlockInterval = 14400`, bounded cache pruning from `v1.0.11`)
- **Block `#20,000` (Unified Fork — C6 + `TxBinaryV1`):** Simultaneously activates C6 10-minute Future Timestamp Limit (`FutureTimestampLimitActivationHeight = 20000`, paired with adaptive miner inherited-tip safety margin `5s` / `30s`) and `TxBinaryV1` Binary Block Size Accounting (`BlockBinarySizeActivationHeight = 20000`, expanding 2 MB block capacity from 185 to 375 ML-DSA-65 user transactions)

---

## 1. Executive Summary

Armaxcoin `v1.0.11` delivers consensus hardening, high-throughput post-quantum block capacity scheduling, miner starvation protection for the upcoming unified Block `#20,000` fork, and bounded memory protection for long-running full nodes—while maintaining **100% rolling backward compatibility** with active `v1.0.10` nodes operating on `ARMX-TESTNET-1` around Block `#15,967` through Block `#19,999`.

Because public nodes and community operators upgrade asynchronously, `v1.0.11` preserves the existing P2P TLS 1.3 TOFU handshake and JSON wire message framing (`NEW_BLOCK`, `BLOCK_RANGE_RESPONSE`, `NEW_TX`) and schedules binary block-size activation on Testnet alongside C6 at **Block `#20,000`** (`BlockBinarySizeActivationHeight = 20000`, `FutureTimestampLimitActivationHeight = 20000`). Prior to Block `#20,000`, `v1.0.11` nodes and miners enforce legacy JSON block and transaction sizing so blocks mined by either version are mutually accepted across the network.

## 2. Backward Compatibility with `v1.0.10` (`#15,967` – `#19,999`)

1. **Unchanged P2P Wire Protocol & Handshake:**
   - Transport stays encrypted over TLS 1.3 with TOFU certificate fingerprint verification (`p2ptls.pem`).
   - All P2P envelope and payload formats (`Message`, `NEW_BLOCK`, `BLOCK_RANGE_RESPONSE`, `NEW_TX`) remain identical to `v1.0.10`.
   - No strict software version check (`core.Version`) disconnects `v1.0.10` peers.
2. **Height-Gated Consensus Size Accounting (`core/network.go`, `core/consensus.go`, `core/blockchain.go`):**
   - `IsBlockBinarySizeActive(blockIndex)` returns `false` on `ARMX-TESTNET-1` below Block `#20,000`.
   - `EffectiveTxSize(&tx, blockIndex)` returns legacy JSON `tx.Size()` below `#20,000` and binary `tx.BinarySize()` from `#20,000` onward.
   - `EffectiveBlockSize(&b)` returns legacy JSON `b.Size()` below `#20,000` and binary `b.BinarySize()` from `#20,000` onward.
   - `SelectCandidateTransactionsLocked` and `/getblocktemplate` continue capping candidate templates using legacy `MaxBlockSize - 50000` and JSON transaction sizing (`~181–185` standard ML-DSA-65 user transactions per block) below `#20,000`, then switch to `MaxBlockSize` (`2,000,000` bytes) and `TxBinaryV1` length-prefixed sizing cleanly alongside C6 at `#20,000`.

## 3. Consensus & Performance Enhancements in `v1.0.11`

### 3.1 Scheduled `TxBinaryV1` Binary Size Accounting (`Block #20,000` Testnet / Block `#0` Mainnet)
Hexadecimal JSON encoding previously inflated NIST FIPS 204 ML-DSA-65 public keys (`1,952 B`) and signatures (`3,309 B`) to ~`10,761` bytes per standard user transaction, limiting a 2 MB block (`MaxBlockSize = 2,000,000` bytes) to 185 user transactions (+1 coinbase = 186 total).

- **Compact Binary Format (`TxBinaryV1` & `BlockBinaryVersionV1`):** Implemented deterministic `MarshalBinary` / `UnmarshalBinary` / `BinarySize` on transactions (`~5,320` bytes per standard signed ML-DSA-65 transaction, `60` bytes per coinbase transaction) and `BinarySize` on blocks (`194`-byte canonical header + 4-byte length-prefixed transactions, i.e., `258` bytes base overhead with coinbase).
- **Preimage Length Guard:** `Transaction.MarshalBinary()` applies 32-byte raw compression strictly to canonical 64-hex-character HTLC SHA-256 preimages (`len(tx.Preimage) == 64`), ensuring non-canonical or oversized arbitrary preimages remain encoded in raw mode and are properly bounded by `MaxTxSize = 20,000` bytes.
- **Measured 2 MB Capacity Gain:** Verified in `TestBlock_BinarySize_2MBCapacity` at **375 regular ML-DSA-65 transactions + 1 coinbase = 376 total transactions** (`1,996,758` binary bytes vs `4,036,307` JSON bytes), more than doubling post-quantum block throughput (`~1.54 TPS` $\rightarrow$ `~3.13 TPS` at 120s target cadence).
- **Profile Schedule:**
  - `ARMX-TESTNET-1`: `BlockBinarySizeActivationHeight = 20000` (unified with C6 at Block `#20,000`, giving ~4,033 blocks / ~5.6 days of rolling upgrade headroom past Block `#15,967`).
  - `ARMX-MAINNET-1`: `BlockBinarySizeActivationHeight = 0` (active from Genesis when Mainnet launches; `core.MainnetLaunched` remains `false` in `v1.0.11`).
  - `ARMX-SOAK-1` & `ARMX-REGTEST-1`: `BlockBinarySizeActivationHeight = -1` (preserving legacy behavior unless overridden via test hooks).

### 3.2 Adaptive Inherited-Tip Margin for C2/C6 Edge Cases (`miner/miner.go`)
From Testnet Block `#20,000`, consensus enforces a strict 10-minute future-timestamp cap (`FutureTimestampLimitSeconds = 600`) alongside non-decreasing parent timestamps (`block.Timestamp >= prev.Timestamp`, rule C2).

- Previously, `armminer` applied a flat `futureLimitSafetyMargin = 30` seconds to all templates. If an adversarial or non-standard miner continuously stamped tips near `+590s..+600s` with `dt = 0`, compliant official miners inheriting `block.Timestamp == minTs` could stall up to 30 seconds on every block.
- In `v1.0.11`, `futureLimitWaitWithMinTime` distinguishes inherited-tip constraint propagation (`blockTs <= minTs`) from genuine local clock skew (`blockTs > minTs`):
  - **Inherited tip (`blockTs <= minTs`):** uses `inheritedTipSafetyMargin = 5` seconds (0s wait up to `595s` skew, capped at `5s` even at `+600s`).
  - **Local clock skew (`blockTs > minTs`):** retains `futureLimitSafetyMargin = 30` seconds, protecting solo miners with drifting local clocks against orphan rejections while preserving safe template bounds in `node/server.go`.

### 3.3 Bounded `globalASERTDriftCache` Pruning (`core/asert.go`)
- Long-running nodes evaluating Armax-ASERT-AW (`ASERTActivationHeight = 13335`) previously retained an unbounded in-memory drift map across extended uptimes.
- `v1.0.11` bounds `globalASERTDriftCache` via `maxASERTDriftCacheEntries = 10000`: whenever cached drift entries exceed `10,000`, batch insertion prunes older heights and retains only the latest `prunedASERTDriftWindowSize = 2048` blocks toward the tip (nearly `3x` `MaxReorganizationDepth = 720`).

## 5. Upgrading from `v1.0.10` to `v1.0.11`

```bash
# 1. Stop running v1.0.10 daemon/miner gracefully (data directory in ./testnet/ is preserved)
# 2. Download & verify v1.0.11 release artifacts (replace platform archive as appropriate)
curl -LO https://github.com/acxxcxx/armax-coin/releases/download/v1.0.11/armax-v1.0.11-linux-amd64.tar.gz
curl -LO https://github.com/acxxcxx/armax-coin/releases/download/v1.0.11/SHA256SUMS
curl -LO https://github.com/acxxcxx/armax-coin/releases/download/v1.0.11/SHA256SUMS.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS

# 3. Extract and restart
tar -xzf armax-v1.0.11-linux-amd64.tar.gz
./armcoind --version
# Expected output includes version 1.0.11
```

All Testnet operators, pools, and miners should upgrade to **v1.0.11** and maintain active NTP synchronization (`timedatectl set-ntp true` on Linux, `w32tm /resync` on Windows) ahead of **Block `#20,000`** to prevent chain divergence when Rule C6 (`+600s` future timestamp limit) and `TxBinaryV1` binary block size accounting activate together.
