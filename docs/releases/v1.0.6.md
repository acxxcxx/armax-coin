## 1. Overview & Purpose

Armaxcoin v1.0.6 is a comprehensive maintenance update for nodes, miners, and operators on the active Armaxcoin public Testnet.

This release focuses on node operational stability, resource management, data race elimination under concurrency, non-destructive peer store migration, isolated path discovery, and graceful shutdown sequence adjustments.

### Network & Consensus Invariance
- **Consensus Invariance:** Block validation rules, Proof of Work timeline (Double-SHA256 for $H < 520$, ArmaxHash v1 for $520 \le H < 2500$, ArmaxHash v2 Stream-Fast for $H \ge 2500$), 120-second target block time, LWMA-1 difficulty adjustment ($N=60$), block reward (60 tARMX), halving intervals (1,050,000 blocks), supply cap (126,000,000 ARMX), and Merkle tree calculations remain completely unchanged.
- **Storage Compatibility:** BoltDB bucket layouts, block and transaction serialization layouts, WAL record structures, and wallet keystores remain unchanged. No database reset or migration is performed.
- **Wire Compatibility:** P2P message framing, message envelopes, and RPC JSON schemas remain unchanged. The RPC gains an additive `X-Network-ID` response header and `peers_seeds` / `peers_candidates` status fields.
- **P2P Transport Identity:** TLS 1.3 encryption and TOFU peer certificate fingerprint verification remain active. Endpoint normalization preserves IPv6 formatting, and peer storage is isolated per network under `<dataDir>/<network>/peers.json`.
- **Network Continuity:** Staging compatibility between v1.0.5 and v1.0.6 was validated in pre-release test environments. Continuous integration and unit test suites cover protocol invariance, while production network upgrades follow standard rolling maintenance procedures.

## 3. Upgrade & Rollback Instructions

### For Node Operators (`armcoind`):
1. **Node Restart Required:** Upgrading requires stopping the individual node process, resulting in brief local downtime for that specific node while the decentralized network continues operating:
   ```bash
   kill -SIGINT <armcoind-pid>
   ```
2. Replace the binary with the compiled `v1.0.6` build.
3. Start `armcoind`:
   ```bash
   ./armcoind -testnet
   ```
4. Verify software version in status RPC:
   ```bash
   curl -s -u <user>:<pass> http://127.0.0.1:19333/status | jq .version
   # Expected output: "1.0.6"
   ```

### Rollback Path:
Rollback to v1.0.5 does not require database changes (no serialization or consensus change). The legacy `<dataDir>/peers.json` file is left intact by v1.0.6, allowing seamless downgrade if needed. Note that a v1.0.5 node should be tested for P2P connection maintenance against v1.0.6 nodes with TOFU enabled.

## 5. Miner Compatibility

- `armminer` reaches the node only through the HTTP RPC (`GET /getmininginfo`, `GET /getblocktemplate`, `POST /block/submit`, authenticated with Basic auth, the RPC cookie, or `X-Mine-Key`) or through an external Stratum v1 pool. It never uses the P2P/TLS transport. This repository contains no Stratum server daemon.
- The server-side mining handlers, authentication (`isAuthorizedMiner`), and the Host-header guard are unchanged from v1.0.5. The RPC adds the additive `X-Network-ID` response header.
- `armminer` now queries `node.GetRPCAuthCookiePath()` first, discovering `$ARMX_DATA_DIR/<network>/armax.cookie`, with fallback to root `armax.cookie`.
- The regression tests `TestMinerHTTPFlowCompatibility` and `TestRPCCookiePathUnderDataDir` (`node/miner_compat_test.go`) replay the miner request flow against the handler in-process.
- **Staging & Miner Verification:** Core Node v1.0.5 and v1.0.6 miner RPC compatibility was validated during pre-release staging. Operators upgrading live nodes should verify miner RPC connectivity during rollout.

## 6. Known Limitations

- Mixed v1.0.5/v1.0.6 P2P session establishment was validated during staging; network upgrades follow standard rolling node update procedures.
- Pre-TLS plaintext `ERROR:` replies (ban, connection limit, subnet limit) surface on the dialing side as `first record does not look like a TLS handshake`.
- After a reorganization, recovered transactions are appended to the mempool before cleanup; a same-sender higher-nonce entry may be dropped and must be resubmitted.
- The `node` full test suite on Windows hosts takes ~250 seconds due to bbolt filesystem lock contention under local antivirus hooks (all tests pass cleanly).
